# 2026-10-13

## 商店 tooltip 第九轮：钉住的那份一闪就没 + 位置偏右

### 现象
- 详情弹窗打开后，钉在右边的原版 tooltip **一瞬间就消失**；悬停(跟鼠标)的那份一直正常。
- 钉住的那份位置偏右，用户希望能靠中间一点。

### 根因一：AUI 的悬停跟踪把钉住的那份顺手清了
`MouseEvent.handleHoverChange`（由 `triggerResolvedEvent` 调）会比较「光标所在元素」与
上一帧记录的 `Document.previousCursorElement`，一旦变化就给旧元素补发
`mouseout` + `mouseleave`（`Element.getRoute()` 差集）。
详情弹窗打开时货架被 `display:none` 收起 → 卡片立刻不再是命中元素 → 卡片上的
`mouseleave` 触发 → `fsTipHide()` → 把**钉住的那份**也一起 clear 了。
（`Operation.onMouseMove` / `WorldWindow.dispatchMouseMove` 都有「位置没变就 return」，
所以只要鼠标抖一下就会在下一帧派发，看起来就是「一瞬间」。）

### 修法：悬停态与钉住态彻底分开
- `ShopTooltipState` 新增 `clearHover()` / `clearPinned()`，`clear()` 保留为全清；
  `show(text,false)` 在 `mode==PINNED` 时直接忽略（不吃悬停请求）。
- 桥接：`hideTooltip()` → `clearHover()`；新增 `hidePinnedTooltip()` → `clearPinned()`。
- 页面：新增 `fsPinRow` / `fsPinShow(row)` / `fsPinHide()`；`fsTipHide()` 只收悬停那份；
  `fsOpenDetail` 末尾走 `fsPinShow`，`fsCloseDialog` / `fsUnload` 走 `fsPinHide`。

### 根因二：位置偏右 = 整块太宽被原版钳到屏幕右边缘
`GuiGraphics.renderTooltip` 把背景左边缘画在「原点+12」，且当「左边缘+框宽」超出屏幕时
**把整块钳到 screenWidth - 框宽**。详情弹窗是居中 340px 宽（shop.css `.dialog`），
右边只剩一两百像素，一条长 lore 就让框宽 > 剩余空间 → 钳到底 → 贴屏幕右边。

### 修法：贴弹窗右边缘 + 自动折行
`ShopTooltipState` 钉住分支重写：
1. `freeAfterDialog = width - (width/2 + 170 + 10) - 8`，折行宽度
   `wrapWidth = clamp(freeAfterDialog - 8, 80, 150)`；
2. 逐行 `font.split(line, wrapWidth)` 折行（保留每段样式，颜色不掉）；
3. `boxWidth = maxLineWidth + 8`，`boxLeft = width/2 + 170 + 10`，
   塞不下才退回 `width - 8 - boxWidth`（贴右边缘），最后 `>= 4`。
常量：`DIALOG_HALF_WIDTH=170 / PINNED_GAP=10 / PINNED_MARGIN=8 /
PINNED_MAX_TEXT_WIDTH=150 / PINNED_MIN_TEXT_WIDTH=80 / PINNED_Y_RATIO=0.24`。

### PinTooltips 调研结论（重要，别再重复挖）
反编译 `PinTooltips-1.20.1-Forge-1.3.1.jar`（在 `.workbuddy/tmp/pintip/`）：
- 它没给界面加新钩子，只做三件事：
  ① `@WrapMethod` 包 `Screen#renderWithTooltip`（`final` 方法，任何界面都生效）；
  ② `GuiGraphicsMixin.pin_tooltips$changeZOffset` 在 `renderTooltipInternal` 头部
     `pose.translate(0,0,6000)`（`PinTooltips.getMaxZOffset()` 硬编码 6000）
     —— 但**仅在 `tooltips()` 非空（玩家自己钉过）或正在画钉住的那份时才抬**；
     另外 `avoidRenderWhenOperating` 会在鼠标悬停在已钉住的 tooltip 上时抑制普通 tooltip。
  ③ 钉住的 tooltip 挂在 `ScreenEvent.Render.Post`（经 Forgified Fabric API 的
     `ScreenEvents.AfterRender` = `ScreenEventHooks.afterScreenDraw`）上补画。
- **纠正上一轮的错误判断**：`ScreenEvent.Render.Pre/Post` 不是从 `Screen#render` 发的
  （`Screen.render` 里根本没有 ForgeHooks），而是 `GameRenderer` 里
  `ForgeHooksClient.drawScreenInternal` 发的：`post(Pre) → screen.renderWithTooltip(...) → post(Post)`。
  **所以它对晴雪UI 的界面照样触发**。这也是 PinTooltips「所有页面都能悬浮」的原因。
- 它对外 API：`PinnedTooltipsService.INSTANCE.pin(Vector2ic, List<ClientTooltipComponent>,
  Font, ItemStack, long)`（`timestamp>0` = auto-pin，会替换上一个 auto-pin 的；否则往列表里追加），
  `unpin(PinnedTooltip)` / `clearTooltips()`；`PinnedTooltip implements ClientTooltipPositioner`。
  **强制依赖 `fabric_api ≥0.92`**（即 Forgified Fabric API，整合包里是
  `fabric-api-0.92.2+1.11.12+1.20.1.jar`）。
- 备选接法（还没做）：`Screen#setTooltipForNextRenderPass(List<FormattedCharSequence>,
  ClientTooltipPositioner, boolean)`（`public`，`m_262861_`）+ 自定义 `ClientTooltipPositioner
  .computePosition(screenW, screenH, mouseX, mouseY, tooltipW, tooltipH)`。
  `renderWithTooltip` 是 `final` 且紧随 `this.render(...)` 之后画它 —— 引擎自己的「页面画完叠 tooltip」通道。

## 追加：状态模型改成「悬停槽 + 钉住槽」双槽（悬停联动）

  和 `drawPinned(...)`，返回框宽供日志。日志变成

- **注意**：老的 `show(text, !pinned)` 语义（悬停时忽略悬停请求）已删除 ——

  搜索/切分类/翻页/交易结算后货架变了，把悬停联动那份收掉，避免显示过期信息；

**用户定调（关键，别再想复杂）**：
> 「怎么还单独写了个事件，关悬浮的 pintooltip 你手动调用关了不就行了，

即：**不写任何按键 / 屏幕事件监听**；自己 pin 的那份自己手动 `unpin`；
玩家自己按键钉的那些由玩家自己撤，本模组绝不 `clearTooltips()` 一把全清。

### 反编译确认的 PinTooltips（1.3.1+forge）关键事实
- `PinnedTooltipsService.pin(Vector2ic, List<ClientTooltipComponent>, Font, ItemStack, long)`：
  **第一个参数不是屏幕尺寸，是这块 tooltip 的初始位置**（内部 `new PinnedTooltip(new Vector2d(那个点), ...)`）。
- `PinnedTooltip.m_262814_`（位置器）**直接返回 position、不做任何钳位**；
  `updateSize(screenW, screenH, font)` **只算尺寸、不动 position**。
  ⇒ 想钉哪儿就传哪儿，位置完全可控。
- `timestamp > 0` = auto-pin（全局一份，会顶掉上一份自动钉的，且 `ScreenEvents.remove` 时会自动 unpin）；
  `timestamp <= 0` = **append 到列表末尾**。本模组统一用 `-1L` 走追加，与玩家的钉住互不干扰。
- `pin` / `unpin` 内部都是 `Minecraft.execute(...)`；**渲染线程上同步执行**
  ⇒ `pin` 返回后立刻能从 `tooltips()`（`Collections.unmodifiableList`）拿到末尾那条并留下句柄。
- `unpin(PinnedTooltip)` = `tooltips.remove(pinned)`；若它恰好是 `autoPinnedTooltip` 才一并清空。
- 钉住的 tooltip 由 `PinTooltips` 挂在 **Fabric `ScreenEvents.afterRender(screen)`** 上每帧补画
  （`lambda$onInitializeClient$4`：遍历 `tooltips()` 逐个 `render`，z 从 400 起每份 +400，上限 6000-1）。
- modid = `pin_tooltips`；`getMaxZOffset()` 硬编码 6000。

### 为什么在 AUI 界面上照样成立（两条链路都验过）
1. **事件注册得到**：PinTooltips 的逐屏注册挂在 Fabric `ScreenEvents.beforeInit`，
   而 **`ApricityScreen.m_7856_()` 第 0 条指令就是 `invokespecial Screen.m_7856_()`**
   （javap 确认）⇒ 不调 super 的担心不成立，注册照常发生。
2. **补画时机走的是 Forge 事件**：Forgified Fabric API 把 `ScreenEvents.afterRender` 桥成
   **`ScreenEventHooks.afterScreenDraw(ScreenEvent.Render.Post)`**（见 `ScreenEventHooks` 方法表），
   而 Render.Post 是 `GameRenderer` → `ForgeHooksClient.drawScreenInternal` 发的 ⇒ **晴雪UI 界面照样触发**。
3. 所以钉住那份**交给它画**，顺带白拿它的 z 抬升（`tooltips()` 非空时所有 tooltip 都抬 6000）。

### 改动
新建 `com/main/fast/compat/apricity/PinTooltipsCompat.java`（**零硬依赖，全反射**）：
- `Class.forName("snownee.pintooltips.PinnedTooltipsService")` 拿 `INSTANCE` 与
  `pin`/`unpin`/`tooltips` 三个 `Method`；失败即 `available=false`，上层退回自绘。
- `pin(int x, int y, List<FormattedCharSequence>, ItemStack)`：`ClientTooltipComponent.create(seq)`
  逐行转换后调 `pin(..., -1L)`，返回 `tooltips()` 末尾那条（句柄）。异常只记一条 warn。
- `unpin(Object)`：只 `invoke` 那一条。

`ShopTooltipState`：
- 新增 `pinnedStack` / `pinnedDirty` / `pinnedNative`（`Object`，即 PinnedTooltip 句柄）。
- `showPinned(List<Component>, ItemStack)`：**同一份内容引用相同就直接 return**（悬停联动每次
  mousemove 都会喊，免得每帧撤了再钉）；换内容才置 `pinnedDirty`。
- `clearPinned()` / `clear()`：先 `releasePinnedNative()`（**只撤自己那条**）再清状态。
- `render()`：`PinTooltipsCompat.isAvailable() && pinnedDirty` 时 `release` → `pin`，
  钉成功就**不再自绘**；没装或这次没钉上则退回 `drawPinned` 自绘（`pinnedByNative` 判定）。
- 抽出 `PinnedLayout` / `layoutPinned(...)`：折行宽度、框宽、贴弹窗右缘的 x 全部算一次，
  **自绘与交给 PinTooltips 共用同一套坐标**。
  `drawPinned` 自绘时要 `boxLeft - 12, boxTop + 12` 抵消原版 `DefaultTooltipPositioner` 的 ±12。

`FastShopUIBridge.showPinnedTooltip(int)`：连 `row.stack` 一起传给 `showPinned`。

`shop.js` **未改**（`fsOpenDetail` → `fsPinShow(row,true)`；`fsCloseDialog`/`fsUnload` → `fsPinHide()`；
`FastShopScreen.removed()` → `ShopTooltipState.clear()` 兜底）。

## 第三轮：用户实测反馈 6 条（02:02）

**用户报的 4 个问题 + 2 个新需求**：
1. 关闭页面没有同步关闭新建的悬停 tooltip
2. 悬停 tooltip 不能拖动
3. 有些 tooltip 不能手动关闭
4. 鼠标悬停的 tooltip 没有 shift / ctrl 功能
5. （新）若存在 shift 的物品 tooltip，点进物品后在**下面**再显示一个 shift 后的描述
6. （新）点进去后那份位置还是太靠右，往左一点

### 铁证：日志里抓到根因
```
[Fast/AUI] 检测到 Pin Tooltips：钉住的那份 tooltip 交给它渲染
[Fast/AUI] Pin Tooltips 桥接异常：pin 之后列表长度没变（0 → 0），这次交给它没成功
[Fast/AUI] tooltip render ok: pinned=true(交给PinTooltips=false 自绘框宽=59) ...
```
⇒ **`Minecraft.execute` 是入队异步的**，`pin()` 返回时那份还没被创建，`tooltips()` 里查不到
⇒ 我们拿不到句柄 ⇒ ①关界面时 `unpin` 根本没执行（残留）③「手动关闭」失效
⇒ 同时我们**每帧还在自绘一份**（`自绘框宽=59`）⇒ ②拖动落在自绘的那份上，当然拖不动

### 修法（本轮）
**`PinTooltipsCompat` 重写：身份标记换成 `components` 引用**
- `pin()` 内部是 `new PinnedTooltip(..., 我们传入的 components, ...)`，**原样存引用不复制**，
  所以任何时候都能用 `PinnedTooltip.components() == 我们那个 list` 把它从 `tooltips()` 里认出来。
- `unpinOur()` 也走 `Minecraft.execute` 入队 ⇒ 和 `pin` 同一个 FIFO 队列，天然保证
  「先创建、后移除」，异步也撤得掉（第三轮的核心修复）。
- 新增 `ourBounds()`（读 `position()` + `size()`，返回 `[x,y,w,h]`）和 `moveOur(x,y)`
  （`setPosition(int,int,double,double)` 前两个参数在字节码里根本没被读，给 0 即可）。

**`ShopTooltipState`**
- 保留**双轨**：既 `pin` 给它，也自己画一份兜底 —— 它那份是「入队创建 + 靠它自己的逐屏事件补画」，
  中间任何一步没接上都不该让说明消失。两份位置完全同步（`drawPinned` 优先读 `ourBounds()`，
  拖过之后照样重合），叠在一起看不出区别。
- 新增 `mousePressedOnPinned/mouseDraggedPinned/mouseReleasedOnPinned`：
  **自己实现拖动 + 右键关闭**（右键 = `clearPinned()`，和 PinTooltips 原生语义一致）。
  拖动按「鼠标绝对坐标 − 抓取偏移」算，**不是累加增量** ⇒ 即使它自己挂在
  `ScreenEvent.MouseDragged.Pre` 上的拖动也生效，两边算的是同一个结果，不会叠加跑飞。
- 位置常量 `PINNED_GAP` 由 `+10` 改成 `-22`（净左移 32px，往弹窗里压一点）—— 需求 6。

**`FastShopScreen`**
- 覆写 `mouseClicked/mouseDragged/mouseReleased`，只有点在钉住那份上才吃事件（`return true`），
  其余全部 `super` 放行给晴雪UI 页面。
- `render` 里加 `FastShopUIBridge.tickModifiers()`。

**`FastShopUIBridge`**（需求 4、5）
- `tooltipLinesFor` 的缓存加上「修饰键状态」这个键（Shift/Ctrl/Alt 各占一位）——
  原版 tooltip 正文是按当前按键状态现算的，一直吃旧缓存就永远看不到变化（就是「没有 shift 功能」）。
- 新增 `pinnedTooltipLinesFor`：普通说明 + **Shift 展开版里多出来的行**接在下面（按行文本做差集，
  因为两次 `getTooltipLines` 出来的是两批新对象，引用对不上）；那行「按住 Shift 查看详情」的提示
  本来就在普通版里，自然不会被当成新增内容。
- 新增 `tickModifiers()`：每帧比一次修饰键状态，变了就重建正在显示的那两份
  （页面只会在鼠标动的时候喊我们，不补这一刀的话单按 Shift 没反应）。

**新增 `FastTooltipFlags` + `mixin/ScreenShiftDownMixin`**（需求 5 的前提）
- 模组那句折叠说明是查 `Screen.hasShiftDown()` 的，那个方法只看 GLFW 真实按键，没法从外面塞状态。
- 所以加一个开关 + 一条 `@Inject(method = "hasShiftDown", at = @At("HEAD"), cancellable = true)`，
  开关打开的那一瞬让它返回 true，趁这一瞬把 tooltip 算出来再立刻还原（外面套 try/finally）。
- refmap 已确认映射到 `Screen.m_96638_()Z`（javap 验过存在）。
- `FastTooltipFlags` 单独放、不引用任何游戏类型：Mixin 类早期加载，引用普通类没事、引用游戏类容易出事。

**① 为什么会「事件时有时无」——AUI 的鼠标事件只在点到 `<input>` 时才取消：**
```
// ApricityUI Client#mouseButton(InputEvent.MouseButton.Pre)
if (event.getAction() == 1) consumed = Operation.onMouseDown(button);
if (event.getAction() == 0) consumed = Operation.onMouseUp(button);
if (Minecraft.getInstance().screen != null) {
    if (consumed) event.setCanceled(true);   // ← 只有 consumed 才取消
    return;
}
// Operation.onMouseDown 的返回值是 MouseEvent#isNativeConsumed()
// consumeNative() 全工程只有 element/Input（<input>）会调 → 点输入框才置位
```
而 Forge 的 `MouseHandler#onPress`（SRG `m_91530_`）里：
```
216: ForgeHooksClient.onMouseButtonPre(button, action, mods)
224: ifeq 228      // 返回 true 就 227: return —— 底下 screen.mouseClicked 整条都不走
...
// 屏幕点击走 m_168084_(boolean[], Screen, double, double, int) → Screen.m_6375_
// 拖拽走 m_168072_(Screen, double, double, double, double) → Screen.m_7979_
// 松手走 m_168078_(...) → Screen.m_6348_
// activeButton(f_91510_) 在偏移 150 就赋值了，早于 216 的事件 → 取消事件也不影响拖拽判定
```

## 第十四轮：**拖不动的真正根因 = `aui-mouse-events: intercept`**，改 meta 解决

用户提示「不能拖动应该是 AUI 自带的鼠标选择文字的问题，看看 AUI 源码有没有事件/API
可以删掉或改这个逻辑」。查 AUI 源码，**用户的直觉方向是对的（在 AUI 侧），只是机制名说错了**。

### 完整因果链（全部有反编译证据）
1. `MouseEvent.tiggerEvent(MouseEvent, Document)`（`behavior`→`event` 包）里：
   ```java
   if (document.interceptsMouseEventsAt(new Position(clientX, clientY))) event.consumeNative();
   ```
2. `Document.interceptsMouseEventsAt(pos)` = `this.interceptMouseEvents && hitTest(...) != null`；
   而 `interceptMouseEvents` 在 **Document 构造器**里由
   `HTML.findMetaContent(path, "aui-mouse-events")` → `parseMouseEventInterception(...)` 解析而来。
   **就是 `<head>` 里的 `<meta name="aui-mouse-events">`。**
   可解析为 true 的值：`intercept` / `block` / `true` / `yes` / `on` / `1`；**其余（含 `none`、缺失、null）→ false**。
3. 我们自己的 `assets/apricityui/apricity/fast/shop.html` 第 6 行写了
   `<meta name="aui-mouse-events" content="intercept">`（抄 AUI 默认模板的），**因此整页命中区域都吞原生事件**。
4. `Client.mouseButton(InputEvent.MouseButton.Pre)`：screen != null 时

## 第十五轮（03:45）按钮符号垂直居中

**用户反馈**：数量那对 `−` `+` 不在按钮正中（截图里一个偏上一个偏下），
「其他这种符号的也得这样居中」。

### 根因：AUI 的 `<button>` 默认把文本行盒**贴在内容盒顶部**
证据是它自己的主题：`theme/mcui.css` / `theme/ore.css` 里按钮写的是
**`padding: 7px 16px 13px`** —— 上 7 下 13 的**不对称** padding，
就是为了把 42px 高按钮里的字「推」到看着正中。这说明它没有做垂直居中，
而是靠 padding 硬凑。

于是 `.quantity-button`（`min-height: 39px` + `padding: 0` + `line-height: 1`，
border 3px → 内容盒 33px，行盒只有 20px）多出来的 13px 全堆在下面 → 字明显偏上。
而 `−`(U+2212) / `+` / `×` 这些非中文字形的行盒度量各不一样，
偏移量还会互不相同 —— 截图里一上一下就是这么来的。

### 修法：全局 `button` 交给 flex 居中
```css
button {
  color: var(--ink);
  cursor: pointer;
  display: flex;
  align-items: center;
  justify-content: center;
}
```
AUI 明确支持这一套（`docs/en/guide/html-css-coverage.md:88`：
flexbox 的 justify-content / align-items 全 ✅，**anonymous text items 也 ✅**），
所以**裸文本**（`−` 这类没包 `<span>` 的）也能被正确摆放。

**关键：必须摘掉会盖住它的 `display: block`** —— 类选择器优先级高于元素选择器：
- `.trade-tab`  删掉 `display: block;`
- `.buy-button` 删掉 `display: block;`（`width: 100%` 保留，flex 下照常生效）

**动了会出问题的（已确认不受影响）**：`.category-button`（flex + center）、
`.category-option`（flex + `space-between`）、`.product`（flex column）——
它们都自己声明了 display / justify，类选择器优先级更高，全局那条盖不到。

**其他符号元素不用动**：`.product-price` / `.total-value` / `.coin` /
`.sign-title` / `.wallet-money` 本来就写了 `align-items: center`。

覆盖到的符号按钮：`×`（shop-close / clear-search / close-dialog）、
`−` `+`（quantity）、`‹` `›`（pager），以及 trade-tab / quick-button /
buy-button / category-menu-close 这些多字按钮（一起正了）。

### ① 全部分类点不回去 —— 根因：`FS_ALL = ""` 被当成「属性不存在」

`fsBindCategory` 原来写的是：

```js
var key = node.getAttribute("data-c");
if (!key) return;          // ← 「全部分类」的 data-c 就是空串，直接 return，事件根本没绑
```

「全部」是 `FS_ALL = ""`，`fsEsc("")` 出来 `data-c=""`，`getAttribute` 拿回空串 →
`!key` 成立 → 提前返回 → `click` 监听器从来没绑上。
选中态本来就是「全部」，所以一开始看不出来；切到别的分类再想点回来就死了。

修法：**DOM 里给「全部」一个占位值 `FS_ALL_DOM = "__all__"`**（`fsDomKey` / `fsKeyFromDom` 互转），
`if (raw === null || raw === undefined || raw === "") return;` 只在属性真的缺失时才跳过。
`fsRenderCategories` / `fsRenderFavorites` 写 `data-c` 都过 `fsDomKey`，两个 bind 都过 `fsKeyFromDom`。

### ② 搜索卡顿 —— 本轮只治了「确定能量化」的那部分，其余靠探针定位

先量了天花板：日志里 `[AUI Document] refresh timing … scripts=110ms` —— 这 110ms 里
**包含整套 `fsInit`**（140 条 × 8 次过桥 + 建分类 + innerHTML 建 32 张卡）。
所以「32 张卡的 innerHTML」本身 ≤110ms，**卡顿不在这里**。
`[AUI Layout] first commit elements=218 total=137ms` 是整页首次排版。
→ 5~10 秒的量级只能来自「AUI 侧对这次 DOM 变更的后处理」或者「同一拍里重复了很多次」。

本轮落地（都是稳的）：
- **搜索防抖 180ms**（`fsSearchTimer` / `fsQueueSearch` / `fsApplySearch`）：连打只重建一次。
- **值没变直接 return**：输入法组字、连击、重复派发都挡掉。
- **同值不重复写 DOM**：新增 `fsTextCache`（fsText 同值跳过）、`fsApplied` + `fsSetDisplay`
  （`grid` / `pager` / `pagerBox` 的 `display`、`page-prev/next` 的 `disabled`、
  `.empty-state` 的 `className`）。这些每个搜索拍都会走，AUI 侧同值写入也会重算样式。
- **写值缓存必须在 `fsInit` 里清空**（页面是新建的 DOM，不清就永远拿不到文本）。
- 直接写过 `textContent` 的地方（`notice`）补 `fsForgetText`。

**探针（关键，下次靠它定位）**：`[perf]` 前缀走 `FastShopUI.log` → 游戏日志
- `[perf] 搜索框输入 +Nms → 「kw」`：N 是距上次输入的毫秒。
  **输入↔输入之间隔了好几秒 → 卡在 AUI 对上一拍的 DOM 变更处理上**（不是我们的 JS）；
  输入↔重建之间隔了好几秒 → 卡在我们自己的重建里。
- `[perf] 重建货架 N 格 Xms`：纯 JS 侧（解析 innerHTML + 造 slot/item），不含 AUI 排版。
- 若一次输入刷出多行 → 是重建风暴（防抖已挡，若还有就说明另有触发源）。
