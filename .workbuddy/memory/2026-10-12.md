## 【第二轮修复】页面全白：window 是 Java 对象，挂属性直接崩脚本

### 根因（日志实锤）
`logs/latest.log`：
`[AUI JS] script execution failed source=fast/shop.html#script`
`dev.latvian.mods.rhino.EvaluatorException: Java class "com.sighs.apricityui.init.Window"
 has no public instance field or method named "__shopGen". (fast/shop.html#script#17)`

上一版在脚本第 17 行写了 `window.__shopGen = ...`（想用它做「页面重载代号」）。
AUI 的 `window` 是 `ApricityUI.getWindow()` 返回的 **Java 对象**，Rhino 的
`NativeJavaObject.put` 遇到不存在的字段直接抛 EvaluatorException，**整个脚本当场死掉**，
于是 41 个静态节点之外什么都没有 = 用户看到的「根本没有任何显示」。

### 【关键】AUI 的 JS 环境（从 jar 里的 assets/apricityui/apricity/global.js 读出，权威）
- 页面脚本跑在 **KubeJS 客户端共享 top-level scope**（跨页面存活），不是每页独立作用域
  → 所有全局必须加前缀；定时器必须在 `document.body.addEventListener("unload", ...)` 里清掉
- global.js 预置的全局：`document` `window` `console` `localStorage` `performance`
  `getComputedStyle` `fetch` `requestAnimationFrame` `setTimeout` `clearTimeout`
  `setInterval` `clearInterval`（`setTimeout` 等直接可用，不必写 `window.setTimeout`）
- 桥接能力（都在 `__auiDecorateNode` 里用 `Object.defineProperty` 装好了）：
  `textContent` `innerHTML` `className` `classList` `dataset` `style`（含 `el.style.x = v`）
  `value` `disabled` `children` `querySelector(All)` `getElementsByClassName`
  `closest` `matches` `focus` `scrollTop` 等 —— 常规 web 写法基本都能用
- **不能做的**：往 `window` / Java 对象上挂任意属性（抛异常）；`document.createElement("item")`
- 键盘事件修饰键是 `controlKey`（不是 ctrlKey）；事件坐标已是逻辑坐标，不要再乘缩放
- `document.readyState` / `document.activeElement` 有 defineProperty 桥，可用
- 事件对象比较**不要**用 `event.target === 某元素`（Rhino 每次包装可能给出不同包装对象），
  改成比 `event.target.getAttribute("id")`

## 第五轮（21:06）：slot 实验是我自己的错，全部回退

### 根因（字节码实锤）
- `render="item" / size / iconScale` **根本不是 `<slot>` 的合法属性**。Slot 只认
  `--aui-slot-render-bg / --aui-slot-render-item / --aui-slot-size / --aui-slot-icon-scale`
  这几个 CSS 变量（global.css 里 body 默认 --aui-slot-size:18）。
  无效属性 → slot 按 global.css 默认渲染：**18×18 + 自带深灰槽位底纹 area.png**
  → 这才是"变暗 + 布局全乱"的直接来源，上一轮的修复方向完全错误。
- 裸 `<item>` + transform:scale 是实例 trait_forge.html 验证过的正确写法（大小位置用户确认过）。
- 另发现 shop 页字体用了不存在的 "OreRegular"（日志 [AUI Font] blank text draw），
  trait_forge 用 @font-face "MinecraftPixel" 指向 apricity/hud/fonts/minecraft-regular.otf。

### 本轮改动（全部页面层，Java 无改动）
- JS：grid/preview 回退为 `<span class="product-icon"><item>…</item></span>`
- CSS：item 恢复 transform: scale(2.5)/scale(3.5) + font-size:0；删 .preview-slot；
  删 button:disabled 里 AUI 不支持的 filter:grayscale；
  字体改为 @font-face MinecraftPixel + 系统 fallback
- HTML：删掉 ore.css 主题链接（jar 里该路径不存在，且 trait_forge 也不引主题）

### 结论/教训
- AUI 的 `<slot>` 深挖要认 CSS 变量而不是 HTML 属性；裸 <item>+transform:scale 是基准写法
- 字体必须 @font-face 外部样式表声明，不存在字体名 → blank text draw

## 第六轮（23:47~00:01）：改正第五轮的误判 + 三项修复

### 【重要更正】第五轮「属性不合法」的结论是错的
反编译 `Slot.class` 字节码实锤，这些 HTML 属性**全部合法**（都在同一方法里作为回退被读取）：
- `shouldRenderBackground()`：`--aui-slot-render-bg` → `render-bg` 属性 → `render` 属性 ∈ {item,none} 返回 false
- `shouldRenderItem()`：`--aui-slot-render-item` → `render-item` → `render` ∈ {bg,none} 返回 false
- `resolveIconScale(f)`：`--aui-slot-icon-scale` → **`iconScale` 属性** → `max(0.01,f)`
- `resolveSlotSizeHint(n)`：`--aui-slot-size` → computed width/height → `size`/`slot-size` 属性

**第五轮真正翻车的原因是 global.css 的继承陷阱**：
```css
body { --aui-slot-size: 18; --aui-slot-icon-scale: 1; --aui-slot-interactive: 1; }
```
`getCustomPropertyInherit()` 会从 body 继承，而 **CSS 变量优先级高于 HTML 属性**。
所以只写 `iconScale="2.4"` 而不在 slot 上写 `--aui-slot-icon-scale`，会读到 body 继承来的 **1**，
iconScale 静默失效 → 物品仍是 16×16，却塞进 18×18 的默认槽里 → 「布局全乱」。
另两个坑：`size` 属性只是 Container 排布的**提示**，不覆盖 CSS 宽高（global.css `slot{width:18px}` 会赢）；
`slot { pointer-events:none }` 让槽位收不到鼠标。

### 物品绘制坐标公式（本次实测字节码，后续改尺寸必用）
`ItemNode.render` 的 x/y 来自 `centeredBodyX/Y(element)`：
```
x = bodyRect.x + (max(1, bodyWidth) - 16) / 2
```
即「物品自己的盒子在 16px 图里居中」。而 `global.css` 有
`slot > item { position: absolute; left: 1px; top: 1px }`（照 18×18 原版槽位写的）。
→ 槽位放大到 40 后必须把 item 的 left/top 改成 `(槽位边长-16)/2`，否则整体偏左上。
本次取值：40→12、56→20、32(窄屏)→8。
`Item.createBodyRenderNodes` 实际调的是 8 参构造，映射为：
stack=`Item::currentStack`、enabled=`Item::shouldPaintItem`、**scale=`Item::resolveIconScale`**、
z=`Item::resolveZIndex`、decorations=**true**、overlay=`Item::resolveOverlayText`、offsetY=`() -> 0.0`。
`shouldPaintItem()` 在存在 Slot 祖先时 = `slot.shouldRenderItem() && !slot.isDisabled()` → `render="item"` 下为 true。

## 第七轮（跨午夜 2026-10-13 00:1x）：tooltip 改用原版渲染

### 用户诉求

### 决定性发现
- **`ApricityScreen.m_88315_`（render）完全覆写了 `Screen#render` 且不调 `super`**
  → Forge 的 `ScreenEvent.Render.Pre/Post` 挂在父类方法里，**永远不会触发**。
  反汇编确认它只调 `FrameTimingHud.beginFrame` / `Base.drawScreenDocument` /
  `Client.drawPersistentScreenDocuments` / `Cursor.drawPseudoCursor` / `Client.drawFrameTimingHud`。
- AUI 自带的 `com.sighs.apricityui.ui.Tooltip` **不是原版 tooltip**，是它自己的 DOM+CSS 实现
  （`Tooltip.show(Document, Position, String, Options)` / `bind(Element, Supplier<String>)`）。

## 第七轮：原版 tooltip「啥都没显示」——全链路排查 + 加固 + 埋点

### 现象
用户报（重启后）：悬停 tooltip 与详情弹窗右侧钉住的 tooltip **都不显示**。

### 排查结论（反编译 AUI 1.2.7）
1. **新 jar 确实生效**：`latest.log` 00:19:08 启动、00:21:35 `prepare 140 entries`，
   FancyMenu 注册了 `com.main.fast.compat.apricity.FastShopScreen` → 我们的子类已在用。
   全程无异常、无 AUI 报错。
2. **事件链没问题**：`Event.getRoute()` + `CAPTURING_PHASE/AT_TARGET/BUBBLING_PHASE` + `composedPath()`
   = 完整 DOM 三阶段派发；`MouseEvent` 构造里 `Event(target, type, true)` → **bubbles=true**；
   `Operation.onMouseMove` 由 `MouseMoveEngine.poll`（挂 `TickEvent.RenderTickEvent.START`）驱动，
   鼠标位置不变则不派发。所以 `mousemove` 会从 `<item>/<slot>` 冒泡到 `.product`，绑在卡片上是有效的。
3. **排除「覆盖文档压住」**：`Client.drawOverlay(RenderGuiEvent.Post)` 第一行就
   `if (Minecraft.getInstance().screen != null) return;` → 界面打开时不会二次绘制页面。
4. **首要嫌疑：z 图层**。`Base` 的 z 体系：`GLOBAL_DOCUMENT_Z_OFFSET=1.0f`、`DEFAULT_DEPTH_STEP=0.005f`、
   `GUI_ITEM_MODEL_Z_OFFSET=150f`、**`FLAT_DOCUMENT_LAYER_STEP=251.25f`**
   （`drawFlatDocumentAtZInContext` 按 251.25 递增给「图层」分层 z）。
   原版 tooltip 只 `pose.translate(0,0,400)` → **只要页面图层 z 超过 400，深度测试(LEQUAL)就把 tooltip 整个判负**。
5. **次要嫌疑：Mask 残留**。`Mask` 首次 pushMask 会 `bindWrite(自己的 FBO)` + `enableStencilTest()` + `clearStencilBuffer()`；
   `Base.drawScreenDocument` 开头只 `Mask.resetDepth()`（**同一帧内之后不还原**）→
   残留 stencil/离屏 FBO 会让后续绘制被裁掉、或画进 FBO，主 framebuffer 上就是一片空白。

### 修法（都不动底层商店逻辑）
- **`FastShopScreen.render`**：`super.render()` 之后先 `restoreRenderTarget()`，再叠 tooltip。
  `restoreRenderTarget()` 用 `AuiServices.render()`（SPI）做：`bindWrite(getMainRenderTarget(), true)` +
  `disableStencilTest()` + `disableScissorTest()` + `disableCull()` + `setColorMask(true×4)` +
  `setShaderColor(1,1,1,1)` + `enableBlend()`，每步单独 try。
- **`ShopTooltipState.render`**：画 tooltip 前 `disableDepthTest()/depthMask(false)/setShaderColor(1,1,1,1)/
  colorMask(true×4)/enableBlend()+defaultBlendFunc()/graphics.disableScissor()`；
  画完在 `finally` 里按 `GL11.glIsEnabled(GL_DEPTH_TEST)` / `glGetBoolean(GL_DEPTH_WRITEMASK)` 查到原值还原，
  别把状态泄漏给同帧后面的 toast / 小地图 / JEI 覆盖层。
- **埋点**（以前这里的 catch 是**完全静默**的，出问题日志里一点线索都没有）：
  - `ShopTooltipState`：`show/hide/render` 节流 INFO（mode、x/y、lines、画前 depthTest/depthMask），
    空状态也打一行；catch 里改成 WARN + 堆栈（节流 1s）。
  - `FastShopScreen`：首帧 INFO「已接管渲染（tooltipActive=? maskActive=?）」。
  - 桥接新增 `FastShopUI.log(String)`；页面新增 `fsPageLog()`，把被 catch 的异常写进日志，
    并在**首次悬停成功**时回一句「首次悬停成功 → showTooltip(N)」。

### 下次看日志的判读表
| 日志表现 | 结论 |
| --- | --- |
| `首次悬停成功 → showTooltip(N)` + `tooltip render ok` 但界面仍没有 | 画了但被别的层盖住 / 或不是本帧 |

## 第八轮（跨零点到 10-13 00:5x）：真凶找到 —— `GuiGraphics.disableScissor()` 抛异常把 renderTooltip 整段废掉

### 日志直接给出答案（埋点生效）
`latest.log` 里：
```
[AUI? no] [Fast/AUI] tooltip show: mode=hover lines=4
[WARN] [Fast/AUI] 叠加原版 tooltip 时抛异常（已吞掉，不影响页面本身）
java.lang.IllegalStateException: Scissor stack underflow
  at GuiGraphics$ScissorStack.m_280462_(GuiGraphics.java:685)     ← ScissorStack.pop()
  at GuiGraphics.m_280618_(GuiGraphics.java:162)                  ← disableScissor()
  at ShopTooltipState.render(ShopTooltipState.java:133)
  at FastShopScreen.m_88315_(FastShopScreen.java:53)
```
**结论：show 一路都到了，东西也准备好了（lines=4/12/14/16），
但 `render` 第一行 `graphics.disableScissor()` 就抛异常，后面
`renderTooltip` 根本没执行。之前几轮「什么都没有」全是这一行造成的。**

### 为什么必炸（反编译 ApricityScreen.render 确认）
`ApricityScreen.render` 的实际流程（字节码逐条读出来的）：
```
FrameTimingHud.beginFrame()
if (showDefaultBackground) this.renderBackground(gg)          // m_280273_
if (linkedDocument != null) {
    loggedRenderState 首次 → LOGGER.debug("[AUI Screen] render path=... doc=...")
    ApricityViewport vp = currentViewport()
    gg.pose().pushPose()                                      // m_85836_
    gg.pose().scale(vp.renderScale(), vp.renderScale(), 1.0F)  // m_85841_
    Mask.pushScissorScale(vp.scissorScale(), gg.pose())
    try { Base.drawScreenDocument(gg.pose(), linkedDocument) }
    finally { Mask.popScissorScale(); gg.pose().popPose(); }   // m_85849_ = popPose（无参）
    Minecraft.renderBuffers().bufferSource().endBatch()
}
ResourcePreviewDialog.draw(gg.pose(), linkedDocument)
Client.drawPersistentScreenDocuments(gg, linkedDocument)
gg.flush()                                                     // m_280262_
Cursor.drawPseudoCursor(gg.pose())
gg.flush()
FrameTimingHud.endFrame()
```
关键点：
1. **裁剪走 `Mask.pushScissorScale / popScissorScale`（GL scissor + 一个 pose 缩放），
   从来不碰 GuiGraphics 的裁剪栈** → 那个栈自始至终是空的 → 我们一 pop 就 underflow。**
   要清裁剪只能用 GL 层的 `GlStateManager._disableScissorTest()`。
2. **pose 是配平的**（pushPose 1 次 / popPose 2 次 = 正常路径 + 异常路径），
   所以 `super.render()` 之后 pose 回到 identity，我们画 tooltip 的坐标不需要额外修正。
3. **投影矩阵没被动**：之前怀疑的 `Base.setProjectionMatrix/getProjectionMatrix` 其实只是
   Base 上的两个**静态转发方法**（内部只有一行 `AuiRenderService.set/getProjectionMatrix`），
   AUI 自己绘制时并不调用它们。`client/Client` 与 `screen/ApricityScreen` 里
   连 "ProjectionMatrix" 这个字符串都没有。
4. AUI 的 `Mask`/FBO/stencil 仍然可能在极端情况下残留，所以 `FastShopScreen.restoreRenderTarget()`
   保留（bindWrite 主 FBO + 关 stencil/scissor/cull + colorMask + shaderColor + blend）。

### 顺带读懂 PinTooltips（1.20.1-Forge-1.3.1，实例已装）
用户提示「可以调用它或学它的写法」。反汇编结论：
- `mixin/interact/ScreenMixin.pin_tooltips$renderWithTooltip` 用 `@WrapMethod` 包住
  `Screen#renderWithTooltip`，方法体只有 `markGrabbing() → original.call(...) → unmarkGrabbing()`；
  **它不还原任何 GL 状态** —— 落点跟我们完全一样（页面画完之后叠加），
  说明「在 AUI 页面上叠原版 tooltip」这条路本身是通的。
- 遮挡问题它是这么解决的：`mixin/pin/GuiGraphicsMixin.pin_tooltips$changeZOffset`
  （`@Inject` 到 `GuiGraphics.renderTooltipInternal` 头部）
  → `poseStack.translate(0, 0, PinTooltips.getMaxZOffset())`，
  即**把 tooltip 的 z 硬抬上去**。这反过来印证了我们的判断：
  原版 tooltip 的 z+400 会被晴雪UI 按 DOM 分层画的页面盖住
  （`FLAT_DOCUMENT_LAYER_STEP = 251.25f`，两层就到 503 > 400）。
  我们的做法更彻底：直接 `RenderSystem.disableDepthTest()`，纯靠绘制顺序压顶。
- `pin` 包里还有 `GuiGraphicsAccess.callRenderTooltipInternal(...)` 这种 accessor，
  以及 `duck/PTGuiGraphics` 给 GuiGraphics 挂的 duck 接口；**不需要依赖它**。

### 改法（只动我们自己的类，底层商店逻辑没动）
`ShopTooltipState.render` 重写：
- **删掉 `graphics.disableScissor()`**，换成 `GlStateManager._disableScissorTest()`。
- 六步状态清理（scissor / 深测 / 深度写 / shaderColor / colorMask / blend）
  **每步各自 try**，用 `tryStep(firstFailure, what, step)` 收集第一个异常，
  最后统一节流 WARN —— 保证「任何一步失败都不会再废掉整段代码」。
- 画完加 `graphics.flush()`，确保这一帧就落笔，不依赖别人 endBatch。
- 保留 `finally` 里按 GL 查询到的原值还原深测/深度写。
